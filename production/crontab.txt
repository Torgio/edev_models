# ── AÑADIR · 11:45 · republicar la curva de 20 años ─────────────────────────────────
#
# La cadena de la mañana queda asi:
#
#     11:15  construir_matriz_produccion    reconstruye la matriz desde la base
#     11:30  guardar_predicciones           la prediccion de D+1
#     11:45  cron_diario --solo-curva       la curva de 20 años
#
# `--solo-curva` porque la matriz de las 11:15 ya esta fresca: reconstruirla otra vez seria
# tirar 45 segundos. Y a las 11:45 para no solapar con la prediccion, que carga once modelos
# y no conviene que compitan por la CPU.
#
# Tarda unos 20 segundos. Publica el `.npy` con los 50 escenarios y reescribe `app_curve` y
# las 178.224 filas de `app_curve_hourly` -- UNA sola curva, se pisa la anterior.
#
45 11 * * * cd /home/ubuntu/scripts && /home/ubuntu/tfm-env/bin/python -u production/curva/cron_diario.py --solo-curva --escenarios 50 >> /home/ubuntu/scripts/logs/cron_curva.log 2>&1


# ── CORREGIR · 11:30 · a la prediccion le falta --equipo ────────────────────────────
#
# Sin esa bandera solo se guardan nuestros ocho modelos. No entran los tres arboles de
# Magdalena y Willy ni el `ensemble11`, que es el que mejor sale en test: 11,623 de MAE
# frente a 12,126 del ensemble de ocho.
#
# NECESITA xgboost en el entorno del servidor:
#     /home/ubuntu/tfm-env/bin/pip install "xgboost>=3.4"
#
30 11 * * * cd /home/ubuntu/scripts && /home/ubuntu/tfm-env/bin/python -u scripts/guardar_predicciones.py --produccion --equipo --desde $(date -d tomorrow +\%Y-\%m-\%d) --hasta $(date -d tomorrow +\%Y-\%m-\%d) >> /home/ubuntu/scripts/logs/cron_prediccion.log 2>&1


# ── AÑADIR · 13:30 · medir la prediccion contra el precio que salio ─────────────────
#
# Las tres lineas de la mañana escriben predicciones. Ninguna las evalua, asi que el unico
# numero que teniamos para defender el trabajo seguia siendo el MAE del tramo de test --
# una foto de enero a julio sobre dias que eligio el reparto. Esto cierra el bucle:
#
#     11:15  construir_matriz_produccion    reconstruye la matriz
#     11:30  guardar_predicciones --equipo  la prediccion de D+1
#     11:45  cron_diario --solo-curva       la curva de 20 años
#     ------------------------------------------------------ 13:00 OMIE publica el PMD
#     13:30  evaluar_diario                 lo predicho contra lo que salio
#
# A las 13:30 y no antes porque el PMD del dia objetivo se publica a las 13:00. Media hora
# de margen, igual que la que separa la prevision de REE del cierre de la casacion.
#
# ESCRIBE EN DOS GRANULARIDADES, Y ES A PROPOSITO:
#   bess_result     una fila por (dia, modelo). El dinero es un hecho de un dia concreto.
#                   Guardarlo por dia deja reconstruir despues cualquier ventana y ver el
#                   dia malo que una media de 30 esconde.
#   model_metrics   una fila por modelo con `periodo='prod_30d'`. Ventana movil que se
#                   RECALCULA entera en cada pasada, no se acumula.
#
# La persistencia entra en la tabla como un modelo mas. Sin esa fila no se puede contestar
# si el modelo aporta dinero o lo aporta la horquilla del mercado -- y en agosto de 2026
# resulta que no se distinguen.
#
# Idempotente: las dos tablas van por upsert, asi que relanzarlo no duplica nada. Los dias
# de 23 o 25 horas se saltan: en EUR/dia no son comparables con uno de 24.
#
30 13 * * * cd /home/ubuntu/scripts && /home/ubuntu/tfm-env/bin/python -u scripts/evaluar_diario.py >> /home/ubuntu/scripts/logs/cron_evaluar.log 2>&1


# ── REVISAR · el cupo de Open-Meteo esta en conflicto ───────────────────────────────

# 30 2 * * * ... ecmwf_tensor_historico.py --a-postgres --sustituir --cupo 7000 ...


# ── OPCIONAL · domingos 05:00 · limpieza de logs ────────────────────────────────────

0 5 * * 0 find /home/ubuntu/scripts/logs -name "*.log" -size +50M -exec truncate -s 10M {} \;


# =====================================================================================
#  NOTAS QUE VALEN PARA TODAS LAS LINEAS
#
#  `CRON_TZ=Europe/Madrid` ya esta arriba del crontab y es lo que hace correctas estas
#  horas. Sin esa linea cron usa UTC y todo se desplaza una o dos horas segun la epoca --
#  justo lo que rompe un proceso que depende de cuando publica el mercado. Es tambien el
#  motivo de que el tensor vaya a las 02:30 y no a las 00:30: las 00:30 de Madrid son las
#  22:30 o 23:30 UTC, o sea el dia UTC ANTERIOR, con el cupo diario ya gastado.
#
#  EL `-u` NO ES OPCIONAL. Sin el, Python acumula la salida al redirigir a fichero y el log
#  parece vacio durante minutos aunque el proceso este trabajando.
#
#  RUTA ABSOLUTA AL PYTHON DEL ENTORNO. Cron no carga el perfil del usuario, asi que
#  `python` a secas seria el del sistema y no encontraria ni pandas.
#
#  SI LA MATRIZ FALLA, LA CURVA NO SE REPUBLICA. Esta en el codigo de `cron_diario.py`, no
#  en el cron: mas vale una curva de ayer con su fecha bien puesta que una de hoy construida
#  sobre datos de la semana pasada. La segunda miente y no lo parece.
